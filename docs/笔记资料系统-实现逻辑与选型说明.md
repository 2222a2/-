# 笔记资料系统 — 实现逻辑与选型说明

> 本文回答四个问题：**每个功能怎么实现？逻辑是什么？为什么用这个技术/思路？做完是什么效果？**
> 配合《笔记资料系统-方案与执行步骤》一起看（那份是"做什么、按什么顺序做"，这份是"为什么这么做、内部怎么跑"）。

---

## 0. 整体思路（一句话）

在现有 M0 资料底座上「长」出一套带结构的笔记系统：数据库只加一张包表、给资料卡加几个字段；前端用 TipTap 做富文本、用递归树做包、用筛选+分组做视图；搜索直接复用已有的 FTS5。能复用的一律复用，不重造轮子。

---

## 1. 标题 + 富文本正文（H1 / H2 / 正文）

### 要实现什么
每条笔记有「标题」（单行必填）和「正文」（支持 H1、H2、正文/段落，以及加粗、列表等基础格式）。

### 怎么实现（逻辑）
- **前端**：用 TipTap（基于 ProseMirror 的 React 富文本编辑器）。工具栏放「H1 / H2 / 正文」按钮，点一下就给当前段落切换块级类型。编辑时 TipTap 在内存里维护一个文档模型（JSON），保存时调用 `editor.getHTML()` 拿到 HTML 字符串。
- **后端**：`knowledge_card` 新增 `rich_body TEXT` 存这段 HTML。入库前用 `nh3`（Python 的 HTML 净化库）按白名单过滤，只放行 `<h1><h2><p><strong><em><ul><ol><li><br>` 等安全标签，剥掉 `<script>`、`onclick`、`iframe` 之类。
- **读取**：打开笔记时后端回传净化过的 HTML，前端用 `setContent()` 还原成可编辑；列表里的「摘要」把 HTML 去标签取前 N 字。

### 为什么用这个技术/思路
- **为什么 TipTap 而不是自己写或纯 textarea**：富文本的「块级格式」（H1/H2 和正文是不同层级，不是简单加粗）需要真正的文档模型。textarea 只能存纯文本，做不出「这一行是一级标题」的结构；自己写编辑器成本极高且易出 bug。TipTap 把复杂度封装好了，H1/H2/段落是开箱即用的 schema。
- **为什么存 HTML 而不是 Markdown**：HTML 能 1:1 还原所见即所得（点 H1 就是 H1），前端渲染简单；Markdown 在复制粘贴富文本时容易丢格式。HTML 也方便以后接 OnlyOffice、导出 Word。
- **为什么后端必须净化（nh3）**：HTML 是用户可控内容，不净化 + 前端 `innerHTML` 渲染 = 恶意脚本能在你浏览器执行（XSS，盗 cookie、篡改页面）。净化放后端是因为「信任边界」在后端——前端净化可被绕过（直接调接口就能塞脏 HTML）。这是安全底线，不是可选项。

### 实现后效果
- 写笔记时像用简易 Word 一样点 H1/H2/正文，排版清晰；
- 刷新、重开、换设备（同一库）内容原样还原；
- 即使有人通过接口塞 `<script>`，入库时被 nh3 剥掉，页面不会被执行。

## 2. 资料类型分类（笔记 / 网站 / 文件）

### 要实现什么
每条资料明确是「笔记」「网站」还是「文件」（类型可扩展），并据此筛选、显示不同图标/字段。

### 怎么实现（逻辑）
- `knowledge_card` 加 `item_type TEXT`，取值 `note | website | file`。新建时由前端「新建下拉」决定类型并随请求带上。
- 类型决定额外字段是否填：网站要 `url`，文件要 `file_ref`（指向 M0 已上传文件），笔记用 `rich_body`。
- 旧数据（M0 的 `web_clip/upload/note/task_doc`）用一次性脚本映射进 `item_type`，保证历史资料也能被新筛选命中。

### 为什么用这个技术/思路
- **为什么新增 `item_type` 而不是只用已有 `source_type`**：`source_type` 表达「从哪来」（剪藏/上传/手动），`item_type` 表达「是什么」（笔记/网站/文件）。语义不同——一条手动写的也可以标成「网站」型（贴个链接当书签）。拆出 `item_type` 让「筛选/分类」维度干净，不跟来源耦合。
- **为什么单字段枚举而不是建多张表**：三类资料 90% 字段相同（标题、正文、时间、归属包），拆三张表会重复 CRUD 和搜索逻辑。单字段 + 条件字段更省，未来加「图片」类型只加一个枚举值。

### 实现后效果
- 左栏/列表能按「全部/笔记/网站/文件」一键过滤；
- 不同类型显示不同图标，网站型点开直接出 URL 跳转，文件型出下载/打开。

## 3. 筛选（按类型 / 时间 / 标题）

### 要实现什么
用户能组合过滤：选类型、选时间范围、搜标题关键词，快速定位资料。

### 怎么实现（逻辑）
- 后端 `GET /api/notes` 接收 `type`、`时间范围`、`q(标题关键词)`，拼 SQL：`WHERE item_type=? AND created_at BETWEEN ? AND ? AND title LIKE ?`，按 `created_at DESC` 返回。
- 时间范围传「今天/本周/本月」枚举，后端用 Python 算出起止时间（避免前端时区/格式坑）。
- 前端把筛选器状态放一个对象里，任意改动就重新请求列表（带 debounce 防抖，避免狂打接口）。

### 为什么用这个技术/思路
- **为什么筛选放后端而不是前端全量拉回自己 filter**：资料越积越多，全量拉再筛既慢又费流量；后端用 SQL 的 `WHERE + 索引` 直接在库里过滤，返回的就是结果集，效率高、可分页。
- **为什么时间用枚举 + 后端算区间**：用户心智是「本周」不是「2026-10-13 到 2026-10-19」；后端 `datetime` 算更稳，且和 FTS5/LIKE 兜底策略统一。
- **为什么标题用 `LIKE` 而非 FTS5**：标题是精确/前缀匹配，FTS5 trigram 也能命中但 `LIKE` 更简单直观；真正「全文搜正文」才走 FTS5。两者组合时 SQL 好写。

### 实现后效果
- 资料一两百条也能秒级定位；选「文件 + 本月」立刻只剩这个月存的文件。

## 4. 分组视图（按标题 / 按时间）

### 要实现什么
列表除了平铺，还能「分组展示」：按标题拼音/A-Z 归组，或按时间（今天/本周/本月）归组，每组一个带头的小节。

### 怎么实现（逻辑）
- 后端 `group_by` 参数：`title` 时按 `title` 排序（中文按拼音首字母分组）；`time` 时按 `created_at` 落到「今天/本周/本月/更早」桶里。
- 返回结构从「平铺数组」改成「分组数组」：`[{group:'今天', items:[...]}, {group:'本周', items:[...]}]`，前端直接按组渲染小节标题 + 卡片。
- 排序/分桶在 SQL 或应用层做一处，前端只负责画。

### 为什么用这个技术/思路
- **为什么分组放后端算而不是前端分**：和筛选同理，分组依赖排序和聚合，数据库做排序最便宜；且「今天/本周」桶边界和筛选共用一套时间计算，逻辑不重复。
- **为什么返回分组结构而非前端自己切**：前端拿平铺数据自己分组也能做，但后端直接给分组结构，前端代码更薄；以后加「按包分组」也只是后端多一个 group_by 值。

### 实现后效果
- 切「按时间」一眼看到今天记了啥、本周攒了啥；切「按标题」同拼音资料聚在一起，资料多时方便扫读。

## 5. 包（多层嵌套容器）

### 要实现什么
能建「包」，包里放笔记/网站/文件；包还能套包（多层），形成像文件夹一样的层级，用来归类。

### 怎么实现（逻辑）
- 新增 `note_package` 表：`id, name, parent_id(指向自己这张表), sort_order, color, 时间戳`。`parent_id` 为 NULL 表示顶层包。
- 新建资料时选「归属哪个包」，写 `knowledge_card.package_id`。
- 前端「包树」：后端返回所有包（带 parent_id 的扁平列表），前端递归构造成树渲染（可折叠/展开）；点某个包 → 列表只显示 `package_id` 是该包及其子孙的资料（递归查子孙 id）。
- 跨包移动：改资料的 `package_id`；删包时 `ON DELETE SET NULL`（子资料不丢，回到未归档）。
- 多层防环：移动包时校验「不能把包移到自己的子孙下」（避免循环引用）。

### 为什么用这个技术/思路
- **为什么 `parent_id` 自引用而不是「每层一张表」或「路径字符串」**：自引用是关系型数据库表达树的标准做法，无限层级、改父级只需改一个字段；比路径字符串（`/a/b/c`）好维护。数据量不大时一次性拉全量前端构树足够，量大可改闭包表/CTE。
- **为什么删包用 SET NULL 不级联删资料**：删包通常是「重新整理归类」，资料本身有价值，误删包不该连资料一起没；SET NULL 让资料回未归档区可再归包，安全。
- **为什么前端递归构树而非后端拼树**：包数量有限（个人用几十到几百），全量拉回前端递归最简单；后端保持「返回扁平列表」的薄接口，前端掌控 UI（展开/折叠/拖拽）。

### 实现后效果
- 像管理文件夹一样管理资料：建「实习项目」包 → 里建「前端笔记」「后端笔记」子包 → 各自塞资料；
- 点顶层包能看到所有子孙资料汇总；拖一条笔记到另一包立即改归属。

## 6. 全文搜索（富文本也要能搜到）

### 要实现什么
搜索框输入关键词，能搜到标题和正文（含富文本里写的 H1/H2 正文），中文短词也行。

### 怎么实现（逻辑）
- 复用 M0 已有的 FTS5 `search_index`（trigram 分词）。资料入库/更新时把「标题 + rich_body 的纯文本」同步进索引（`upsert_search`）。
- `rich_body` 是 HTML，入库前先 `re.sub('<[^>]+>',' ', html)` 抽成纯文本再进索引，这样搜「需求」能命中 H1 里写的「需求分析」。
- 短词（<3 字）FTS5 trigram 不生效，沿用 M0 的 `LIKE` 兜底，保证「周报」两字也能搜到。

### 为什么用这个技术/思路
- **为什么复用 FTS5 而不是 `LIKE` 全场**：LIKE 数据多时全表扫、慢且不能按相关度排序；FTS5 trigram 对中文子串友好（不用分词器）、带 `rank` 相关度、快。M0 已跑通，复用零新增成本。
- **为什么 HTML 要抽纯文本再索引**：FTS 索引的是「词」，HTML 标签（`<h1>`）不是内容，不抽的话搜「h1」会命中、搜真正标题文字反被标签噪声干扰；抽纯文本保证搜的是人写的内容。

### 实现后效果
- 搜「周报」直接列出所有标题/正文含周报的笔记和网站，含富文本里的标题文字；点结果跳到对应资料。

## 7. 横向决策（为什么整体这么定）

### 为什么 extend worklearn-platform 而不是独立新应用
笔记系统的 DB、搜索、AI 工具 M0 全有。独立做要重造入库/搜索/向量/RAG，且资料割裂在两套库、AI 无法跨库引用。extend 让笔记天然进全局搜索、能被 AI「记一下/搜一下」调度，数据一处存、处处用。代价仅是给一张表加字段，风险低。

### 为什么富文本存 HTML 而非 Markdown
用户要的是「点 H1 就变一级标题」的所见即所得体验，HTML 是这个体验的一等公民；Markdown 适合纯文本写作流，不适合「选段→设标题」的交互。且 HTML 易映射到 Word/OnlyOffice，和文档中心打通更顺。

### 为什么后端净化是底线
HTML 走 `innerHTML` 渲染，未净化的用户内容 = 可执行脚本 = XSS。前端净化能被直接调接口绕过，所以净化必须在后端（信任边界）。nh3 白名单只放排版标签，脚本/事件属性一律剥。

## 8. 实现后的整体效果（用户视角）

- 打开「笔记」页：左边是包树（多层文件夹），上边是「全部/笔记/网站/文件 + 今天/本周/本月 + 搜索框」，中间是分组好的资料卡片。
- 点「新建笔记」：填标题 → 用 H1/H2/正文排版写内容 → 选个包 → 自动保存。
- 点「新建网站」：贴 URL → 存成网站型资料，带跳转。
- 点「新建文件」：上传 → 进文件型，可再下载。
- 搜「实习」：所有相关笔记/网站/文件浮现，包括富文本标题里的字。
- 一切本地 SQLite，离线可用，数据在自己电脑。
