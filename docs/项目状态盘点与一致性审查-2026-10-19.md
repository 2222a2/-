### 3.3 🔴 本次新发现的混乱 / 不一致（重点）

**A. TipTap + nh3 笔记富文本子系统——技术方案扩张但审计漏覆盖（应补文档）**
- `package.json` 把 `@tiptap/react`、`@tiptap/pm`、`@tiptap/starter-kit` 列为**生产依赖**（必装），仅 `NoteEditor.tsx` 使用；后端配 `nh3` 净化。
- 10-16 一致性审计的"技术栈基线"和逐项审计表里**完全没有 TipTap/nh3**——审计只盯了 M1–M4/M7，漏掉了 M0 笔记编辑器的技术选型。
- 影响：技术栈"单一事实来源"不完整；若后续有人按审计基线判断"前端只有 React/Vite/OnlyOffice"，会误判。建议补进《技术实现设计》与审计表。

**B. 端口口径分裂（真实混乱·应修）**
- 默认/README/`vite.config.ts`/`config.py`：`8000`。
- 但 此前 `scripts/verify_docs.py`、`verify_scenario_a.py`、`verify_m7.py`、`verify_m3_monthly.py`、`verify_phase1_gaps.py` 与 `Phase1验收说明.md` 示例曾用 `8021`，**已于 2026-10-19 全部统一为 `http://localhost:8000`**。
- 后果：按 README 在 8000 起后端后直接跑走查脚本会连不上（除非手动设 `BASE_URL`）。这是文档与脚本之间的硬不一致。
- 状态：已于 2026-10-19 修复——所有 verify 脚本默认 `BASE_URL` 与验收说明示例统一为 `8000`（仅 OnlyOffice 文档服务仍用其固定 `8080`，不属于本次后端端口统一范围）。

**C. 双虚拟环境残留（真实混乱·应清）**
- `backend/.venv`（25M，仅含 `httptools/nh3/pip`，**损坏的半成品**）与 `backend/.venv2`（115M，真实可用）并存。
- 原因（README 已记）：`.venv` 曾因 Python 版本错配损坏，且被本机文件监视器锁句柄无法删除。
- 风险：新人照常规 `.venv/Scripts/activate` 会激活损坏环境直接报错；README 命令正确指向 `.venv2`，但命名反直觉。
- 修复建议：释放句柄后删除 `.venv`，把 `.venv2` 重命名为 `.venv`（标准名），同步把 README 命令里的 `.venv2` 改回 `.venv`。

**D. 缺 `.env` 文件（setup 缺口·应补）**
- 仓库只有 `.env.example`，无 `.env`；未配 `ARK_API_KEY` 时 AI 全部走 Mock（离线可跑，但非真实 AI）。
- 影响：首次克隆者若不读 README 第 64–74 行，会以为 AI 坏了。属文档可达性问题，不算代码混乱。

**E. `data/` 残留测试产物（应清理）**
- `data/edited_2.docx`、`data/study_tasks_pending.json.bak`、`data/docs/8.docx·10·12·14·16·18.docx`（偶数 ID 明显是 verify 脚本生成）。
- 走查脚本声称"不污染真实库"，但生成的 `.docx` 文件未被清理，说明清理逻辑不完整。
- 修复建议：把 `data/docs/` 下 verify 生成的测试文件与 `data/*.bak` 清掉；并给 verify 脚本补"跑完删测试 docx"的逻辑。

## 4. 一致性审查结论（回答"之前的东西是否同一套技术栈/约束"）

- **主体架构与原始方案一致**：React/Vite/FastAPI/SQLite/OnlyOffice SDK/python-docx 三件套/reportlab 这一套贯穿 M0–M7，无第二套并行技术栈、无框架混用（前端没有 Vue/原生双轨，后端没有 Flask/Django 双轨）。**没有"混乱到两套栈并存"的情况。**
- **约束偏离均已记录在案或已修复**：10-16 审计发现的报告导出/落库/文档维度三项已闭合；RAG/chromadb 与 zustand 为有意 MVP 取舍，未回退、未假装没发生。
- **真正的"脏"只有 5 处**（见 §3.3）：其中 B/C 是应修的工程卫生问题，A 是审计自身的覆盖盲区，D/E 是文档与清理问题。**这些问题不影响"功能已达成"的结论，但会让项目在交接/复跑时踩坑。**
