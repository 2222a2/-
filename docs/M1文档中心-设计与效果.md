# M1 文档中心 · 设计与效果说明

> 配套代码：`backend/app/docs.py`、`backend/app/onlyoffice.py`(补 key/权限)、`backend/app/db.py`(Doc CRUD)、
> `frontend/src/components/DocEditorProvider.tsx`、`frontend/src/components/CommandPalette.tsx`、`frontend/src/components/AnalysisPage.tsx`、`frontend/src/api/client.ts`。
> 联调脚本：`scripts/verify_docs.py`（15/15 PASS）。

## 总设计原则

把"生成文档"拆成两段，各司其职、互不污染：

1. **AI 只填空，应用层管落盘**：豆包只负责产出"结构化 JSON"（标题/章节/段落/要点），
   渲染、落盘、建版本、配回存全是确定性代码。AI 的灵活性被 JSON schema 框死，
   不会出现"模型吐一段 markdown 然后渲染崩了"的不可控情况。
2. **文件命名用 doc_id 而非标题**：标题会变、会重名，用自增 id 当文件名最稳，
   回滚/删除/回调都能按 id 精确定位，天然防重名覆盖。
3. **当前文件 + 版本快照分离**：`data/docs/<id>.<ext>` 永远是"最新版"，
   每次保存把"这一版"另存为 `snapshots/<id>/vN.<ext>`，版本链路可追溯、可一键回滚。
4. **回存走 OnlyOffice 官方回调协议**：编辑后 OO 把文件挂到 responseUrl，我们下载覆盖本地，
   零自造轮子，和 OO 的编辑/协同能力原生打通。

## 五个子项：为什么 & 效果

### 1. AI 生成真实 Office 文件（`/api/docs/generate`）

**为什么这么做**
- 周报/方案/拆解表这类"结构化文档"，本质是可模板化的内容。让 AI 先产出结构（而非直接写文件），
  渲染引擎再把它变成真正的 `.docx/.xlsx/.pptx`——相比"让模型直接生成文件二进制"稳定得多。
- 离线无 `ARK_API_KEY` 时走 Mock 兜底：周报类直接消费 `M3` 已聚合的周报数据，
  分析产物类直接把"需求卡+拆解步骤"转成文档骨架，保证**没有密钥也能跑通整条链路**。
- 文件名用 doc_id、先渲染临时文件再 `replace` 成正式名，避免半截写入或重名冲突。

**效果**
- 一句话/prompt → 真·可双击打开的 Word/Excel/PPT，不是 HTML 仿制品。
- 落库 `Doc` 表（含 `linked_task_id`），后续能被任务、周报、搜索索引消费。
- 联调实测：生成"本周工作周报"得到 36KB 真实 docx，python-docx 可正常解析。

### 2. OnlyOffice 回调回存（`build_editor_config` + `/api/docs/callback/{id}`）

**为什么这么做**
- 原 `onlyoffice.py` 只有 config 骨架、没有真实 `callbackUrl`，等于"能打开不能存"。
- 补三件事：`callbackUrl` 指向后端、`document.key` 用 `{doc_id}-{version}`（改版本必换值，否则 OO 命中缓存打开旧文件）、`permissions.edit=true` 放开在线编辑。
- 回调按 OO 官方协议：`status=2/3` 才下载 `url` 里的编辑后文件覆盖本地；其余状态(1打开中/4无改动)只回 `{"error":0}` 确认收到。必须回 `error:0` 否则 OO 会重试。

**效果**
- 用户在编辑器里改完点"保存"，文件自动回存本地 `data/docs/<id>.<ext>`，不再需要"另存为再上传"。
- 服务端下载用 `httpx` 带超时+重定向跟随，网络抖动不会卡死请求。

### 3. 版本管理（`versions_json` + 快照目录）

**为什么这么做**
- Office 文档最怕"改崩了找不回"。每次保存（生成/回存）都打一个带时间戳的快照，
  存成 `snapshots/<id>/vN.<ext>`，`versions_json` 记录每版的 `version/saved_at/size/note`。
- 回滚 `rollback/{v}` 不是删历史，而是把目标快照复制回"当前文件"并作为**新版本**记录——
  既能回到过去，又保留完整演进轨迹，可追溯、可审计。

**效果**
- 任意版本可 `/export?version=N` 单独导出；`/versions` 一览全部历史。
- 联调实测：生成(v1)→编辑回存(v2)→回滚到 v1(产生 v3)，链路正确，v3 内容 == v1。

### 4. 前端 `DocEditor.tsx` 接通（双入口）

**为什么这么做**
- 编辑器很重，全站只挂一个实例最省资源——所以用 `DocEditorProvider` 全局 context + 弹窗，
  任何页面调 `openDoc(config)` 就弹出，关掉即销毁。
- 两个真实入口贴合用户工作流：
  - **命令面板**（Ctrl/Cmd+K）"生成周报文档 / 生成 excel 任务表" → 规则层识别 `gen_doc` → 调生成接口 → 直接打开。
  - **分析产物**（M4 第五步）"生成 Word 初稿" → 把"需求确认卡+拆解步骤"直接塞给生成器，分析→文档无缝衔接。

**效果**
- 从"想出一份文档"到"在 OnlyOffice 里改"零跳转，呼应平台"单空间零跳转"定位。
- 命令路由把 `gen_doc` 放在"周报 Markdown"规则之前，避免"生成周报文档"被误判成生成 Markdown。

### 5. 联调验证

**为什么这么做**
- M1 涉及"AI→文件→外部 OO 服务→回调→版本"多跳，必须端到端证明，不能只测单点。
- 脚本 `scripts/verify_docs.py` 用本地临时 HTTP 服务模拟 OnlyOffice 回调（挂一个"改过字"的 docx），
  覆盖：生成→落盘→回调回存→版本快照→文件服务→回滚。

**效果**
- 15/15 PASS，闭环成立。验证后已清理测试数据，DB 回到干净状态。

## 部署注意（真机跑 OO 时会遇到）

- `BACKEND_PUBLIC_URL`：OO 服务端要**回源**拉文件/回调，必须填 OO 容器能访问的地址。
  同机调试默认 `http://localhost:8000`；OO 跑在 Docker 里要填 `http://host.docker.internal:8000`
  或电脑局域网 IP，否则 OO 拉不到文件、回调打不到后端（这是 OO 部署的经典坑，不是代码 bug）。
- OnlyOffice 已用 `docker-compose.yml` 起在 8080，且 `JWT_ENABLED=false`（MVP 简化，上生产前务必开 JWT）。
- 想接真豆包：配 `ARK_API_KEY` 即可，否则全程 Mock 兜底。
