2三、为什么做

  • 平台定位需要"记忆中台"：工作学习一体化平台要"零跳转、不用找资料"，前提是资料能方便存进来、且存了就能被搜到 / 被 AI 引用。没有底座，AI 和搜索都是"无米之炊"。
  • 消除"存了搜不到"的割裂：如果网页 / 文件 / 笔记各写各的存储，必然出现"我明明存过却搜不出来"。统一流水线从根上规避。
  • 补齐 M2 的缺口：M2 把 RAG 检索、命令面板后端规则都做了，但只查不存、且四通道没落地。M0 是让 M2 真正可用的底座。
  • 中文短词是高频场景：FTS5 trigram 对 <3 字符（两字中文）无效，必须兜底，否则日常"搜周报""搜OKR"会零命中。

3四、核心逻辑

① 统一入库流水线 ingest_card()（底座心脏）

所有来源都走同一条路：

a. 写 knowledge_card 表（结构化元数据：title / content / source_type / 来源url或文件名）
b. 同步进 search_index（FTS5 全文索引）
c. 若 RAG_BACKEND=chromadb → 向量化写 chromadb

任一步失败不影响主流程：向量缺失自动降级到全文检索。

② 四个入库通道

通道逻辑作用
网页剪藏后端抓取 URL 正文；readability 优先，正则降级把"看到的好网页"一键变资料
文件上传txt/md 直读；pdf/docx 可选库抽取、原文留档把"本地文档"变成可检索资料
手动笔记直接写 content；命令面板"记一下"也走这随手记要点，自动入库
任务文档M1 文档中心定稿时调用 ingest_card成果文档自动沉淀为资料

③ 检索与短查询兜底

FTS5 trigram 仅索引 3+ 字符 gram，两字中文（如"周报"）会零命中。给 search_cards() / search_kb() 加 LIKE 子串兜底：当 trigram 返回空且查询偏短时，退化为 LIKE。已实测 2 字 / 3 字中文均可命中。

④ 向量写入端

补齐 M2 遗留的"只能查不能存"缺口，让语义检索真正可用（装 chromadb 后设 RAG_BACKEND=chromadb 启用）。

⑤ 命令面板（入口层）

把"想做啥"从点菜单变成"说一句"：规则快路径（建任务 / 记笔记 / 搜资料 / 生成报告）+ AI 兜底，本地执行动作。已修正规则顺序，避免"搜一下周报"被误判成生成周报。
