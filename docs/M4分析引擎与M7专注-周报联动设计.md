# M4 任务分析引擎 · Prompt 限定原理 + 需求确认卡 + M7 专注↔周报联动

> 范围：Phase 1。本文给可直接照抄的 prompt 模板与数据流，仍是方案级（未写产品代码）。

---

## 一、M4 的 prompt 限定：怎么做、什么原理

### 1.1 为什么要"限定"
让 LLM 自由发挥，会得到冗长、格式飘、不可机读的答案——而产品要的是**可落库、可转任务、可追问**的结构化结果。所以 M4 把模型从"自由写手"变成"受控的访谈 + 拆解器"：流程由应用代码掌控，模型只在每个阶段填固定格式的"槽位"。

### 1.2 四道闸（怎么限定）
- **闸1 角色与协议锁定**：system prompt 写死"四阶段协议"和"输出契约"，模型不能越界。
- **闸2 阶段门控**：每次只让模型产**一种**输出，且只注入当前阶段需要的上下文（不清全量）。
- **闸3 结构化输出**：用 JSON / function 参数强制字段，拒绝自由文本（解析失败即重试）。
- **闸4 数量与范围限制**：澄清只反问 2–4 个；步骤粒度锁死（单步 0.5–4 小时）。

### 1.3 底层原理（逻辑）
> 确定性状态机 + 生成式填空。

阶段切换、谁拍板、落库动作 = 应用代码（确定）；理解用户、把非结构化→结构化 = 模型（生成）。模型负责"懂"，应用负责"控"。这样既保留 AI 的灵活性，又保证结果可控、可编辑、可机读。

### 1.4 四阶段与对应 prompt（示意，可直接抄）

**阶段 A 需求澄清（CLARIFY）**
```
你是一个任务拆解专家。收到用户的模糊任务后，只做一件事：找出"还缺的关键信息"，并提出 2-4 个反问。
必须覆盖的要素维度：目标 / 交付物 / 截止时间 / 约束条件 / 成功标准。
规则：
1. 只问用户没说过的，已说的不要重复问。
2. 最多 4 个，按重要性排序。
3. 不要替用户做决定，不要列步骤，不要写方案。
4. 一次只输出 JSON：
{"questions":[{"field":"goal|deliverable|deadline|constraint|criteria","question":"..."}]}
```

**阶段 B 需求确认卡（CONFIRM）**
```
基于用户对你反问的回答，产出"需求确认卡"，用 JSON：
{
  "goal":"一句话目标",
  "deliverable":"具体交付物/范围",
  "deadline":"截止时间(ISO) 或 无",
  "constraints":"限制条件",
  "success_criteria":"怎样算完成",
  "assumptions":["模型做的假设，待用户确认"]
}
不要加任何解释，只输出 JSON。
```

**阶段 C 步骤拆解（DECOMPOSE）**
```
基于已确认的需求，把任务拆成有序、可执行步骤。每条步骤用 JSON：
{"order":1,"desc":"动作描述","est_hours":2,"deps":[步骤序号],"need":["资料/工具"],"output":"该步产出"}
规则：
1. 单步可在 0.5-4 小时内完成。
2. 步骤间有依赖必须写 deps。
3. 只输出 steps 数组，不要解释。
```

**阶段 D 计划清单 + 逐步追问（PLAN）**
- `steps` 直接写入 `Task`（`parent_id` = 主任务），生成可勾选、可排期的子任务。
- 选中某步 → 模型按 **风险 / 卡点 / 前置条件** 三问追问 → 用户回答 → 沉淀进 `PlanAnalysis.qa_log_json` 作为"问题预案"。可循环回写。

## 二、需求确认卡：内容 + 能否直接修改

### 2.1 卡片字段（即阶段 B 的输出）
| 字段 | 含义 |
|---|---|
| 目标 goal | 一句话说清"为什么做、做成啥" |
| 范围/交付物 deliverable | 具体产出（如"一份 10 页客户周报 docx"） |
| 截止 deadline | ISO 时间或"无" |
| 约束 constraints | 限制（预算/格式/不可用的资源） |
| 成功标准 success_criteria | 怎样算做完（验收点） |
| 关键假设 assumptions | 模型基于常识补的假设，待你确认 |

### 2.2 示例
```
目标：给周五客户会议准备一页纸周报
交付物：1 页 Word 周报（本周进展 + 风险 + 下周计划）
截止：2026-10-16 17:00
约束：只用内部数据，不出现未公开数字
成功标准：客户能一眼看懂本周状态与风险
假设：数据来源是本周已标记 done 的任务
```

### 2.3 能否直接修改？——能，而且是"编辑后确认"，不是"是/否"
设计上确认卡是**可编辑表单**（每字段一个输入框），用户可改任意字段、增删假设，再点「确认并拆解」。这是 human-in-the-loop，保证准确 + 控制感。拆解后的步骤同样可增删改、调工期、改依赖。**AI 给初稿，人最终定稿**——避免 AI 一本正经地写错需求。

## 三、专注计时 ↔ 周报 联动

### 3.1 数据流（靠一张表解耦）
```
点任务「专注」  → INSERT FocusSession(task_id, start_ts)
停止专注        → UPDATE FocusSession SET end_ts, duration_sec
生成周报时      → SELECT SUM(duration_sec) WHERE task_id IN (本期 done 任务) AND 周期内
               → 写入 Report.content 的「投入工时」段
```
M7（专注）只负责写 `FocusSession`，M3（周报）只负责读它——模块解耦，靠表连接，谁也不依赖谁的界面。

### 3.2 为什么是"联动"而不是"手动填工时"
计时是**做事的副产品**，不是额外工作：你开始/停止专注，时长就记下了。用户零跳转、零额外录入，周报却自动有真实工时。这正是"零跳转"的落点之一。

### 3.3 周报里的呈现
- 每个任务一行：标题 / 截止 / 完成度 / 关联文档 / **聚焦时长**
- 报告底部：本周专注总时长、按任务 Top、与上周对比（趋势）
- 来源可从 `FocusSession` 直接聚合，也可叠加 `Task.completion_pct`

### 3.4 联动带来的衍生能力
- **完成度校验**：子任务标 done 但专注时长 = 0 → 标「疑似虚完成」提醒。
- **工时基线**：估 2h 实 4h → 积累个人估算准确度（未来拆解更准）。
- **防空洞增强**：任务久未更新且专注 = 0 → 强提醒。

---

## 小结
- M4 的"限定"= 状态机控流程 + JSON 控格式 + 闸控数量，原理是"确定性流程包着生成式填空"。
- 需求确认卡是结构化 JSON，前端渲染成**可编辑表单**，人定稿后再拆解。
- 专注↔周报靠 `FocusSession` 表单向写入、周报聚合时读取，自动、解耦、零录入。
